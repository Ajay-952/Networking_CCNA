## HTTP and HTTPS
### What is HTTP?
HTTP (HyperText Transfer Protocol) is the application-layer protocol that browsers and servers use to exchange data on the web.
- It follows a simple request-response model:
1. The client (browser) sends a request to a server.
2. The server processes it and sends back a response.

HTTP is stateless, meaning each request is independent and the server doesn’t remember previous ones. Cookies, sessions, and tokens are used to add state on top.

Anatomy of a request

```
GET /index.html HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept: text/html
```

Anatomy of a response
```
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1256

<html>...</html>
```

#### Common methods
Method	    Purpose
GET	        Fetch a resource
POST	    Send data to create something
PUT	        Replace a resource
PATCH	    Partially update a resource
DELETE	    Remove a resource

#### Common status codes
- 2xx: success (200 OK, 201 Created)
- 3xx: redirection (301 Moved Permanently, 304 Not Modified)
- 4xx: client error (400 Bad Request, 401 Unauthorized, 403 Forbidden, - 404 Not Found)
- 5xx: server error (500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable)

HTTP runs on port 80 by default.

The problem with HTTP

HTTP sends everything in plain text. Anyone between you and the server (on public Wi-Fi, at your ISP, or at a compromised router) can:

Eavesdrop: read passwords, form data, cookies
Tamper: modify the content in transit (e.g., inject ads or malware)
Impersonate: pretend to be the real server (man-in-the-middle attacks)

### What is HTTPS?

HTTPS (HTTP Secure) is simply HTTP running over TLS (Transport Layer Security, the successor to SSL). The HTTP messages themselves are unchanged. They are just wrapped in an encrypted tunnel. It runs on port 443 by default.

#### HTTPS provides three guarantees:

Confidentiality: data is encrypted, so eavesdroppers see only gibberish.
Integrity: data can’t be altered in transit without detection.
Authentication: a certificate proves you’re talking to the real server.

#### How the TLS handshake works
1. Client Hello: the browser sends supported TLS versions and cipher suites.
2. Server Hello + Certificate: the server picks a cipher suite and sends its digital certificate (containing its public key).
3. Certificate verification: the browser checks that the certificate was signed by a trusted Certificate Authority (CA), hasn’t expired, and matches the domain.
4. Key exchange: both sides use asymmetric cryptography (e.g., ECDHE) to agree on a shared session key.
5. Encrypted communication: from here on, all data is encrypted with fast symmetric encryption (e.g., AES) using that session key.

Asymmetric crypto is used only for the handshake because it’s slow; symmetric crypto handles the bulk data

#### Why HTTPS matters
- Browsers flag HTTP sites as “Not secure.”
- Modern features (geolocation, service workers, camera access, HTTP/2, HTTP/3) require HTTPS.
- It’s essential for logins, payments, and any personal data.
- Free certificates from Let’s Encrypt (or AWS Certificate Manager, if you use AWS) made it easy and cheap.

#### Quick note on versions
- HTTP/1.1: one request at a time per connection, text-based.
- HTTP/2: multiplexing, header compression, binary framing.
- HTTP/3: runs over QUIC (UDP) instead of TCP, with faster connection setup and TLS 1.3 built in.
